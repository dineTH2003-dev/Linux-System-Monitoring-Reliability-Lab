# Standard Root-Cause Analysis (RCA) & Incident Report Template

**Project:** Linux System Monitoring & Reliability Lab  
**Scope:** Blameless Post-Mortem Standard & Incident Timeline Template  

---

## 1. RCA Philosophy & Core Principles

Incident analysis within the Linux System Monitoring & Reliability Lab adheres to Google Site Reliability Engineering postmortem standards:
- **Blameless Culture**: Analyses focus on system mechanics, tooling boundaries, and failure cascades, never human error.
- **Fact vs. Hypothesis Distinction**: Confirmed root causes backed by empirical telemetry are strictly separated from speculative hypotheses or secondary symptoms.
- **Actionable Preventive Outcomes**: Every investigation terminates in concrete architectural or monitoring improvements with tracked owners.

---

## 2. Standard RCA Document Structure

Every incident report generated by the reliability testing framework must adhere to this 10-part structure:

### 1. Incident Summary
A concise executive summary (1–2 paragraphs) detailing what failed, which services were degraded, how it was detected, and how full recovery was achieved.

### 2. User & System Impact
Quantified impact metrics:
- Service Level Indicator (SLI) degradation.
- Consumed Error Budget % ($T_{\text{downtime}} / T_{\text{allowed}}$).
- Total duration of outage ($T_{\text{restored}} - T_{\text{inject}}$).
- Direct effects on dependent callers and operator workflows.

### 3. Chronological Incident Timeline
An exact, ISO-8601 timestamped sequence of events:
- `T0` (Failure Injection): Precise moment the anomaly began.
- `T1` (Detection): Moment monitoring or health check registered failure.
- `T2` (Alert Delivery): Moment Prometheus transitioned rule to `FIRING`.
- `T3` (Investigation / Triage): Moment automated or manual inspection started.
- `T4` (Remediation Triggered): Moment recovery action was dispatched.
- `T5` (Verification / Restoration): Moment service was verified healthy.

### 4. Detection Method
The technical mechanism that first caught the anomaly:
- Rule name (e.g. `TargetDown`, `HostFilesystemSpaceWarning`, `SystemdServiceFailed`).
- PromQL expression and evaluation interval.
- Scrape interval or health check cadence.

### 5. Symptoms & Telemetry Observations
The observable external and internal markers of degradation:
- HTTP status codes (5xx, Connection Refused).
- PromQL metric deviations (CPU %, free inodes %, latency spikes).
- System log entries (`journalctl`, `syslog`, agent logs).

### 6. Root Cause (Confirmed vs. Hypothesis)
- **Confirmed Root Cause**: The verified physical or logical mechanism that broke the system. Supported by logs and reproducible testing.
- **Preliminary Hypotheses Disproven**: Alternative explanations that were investigated and ruled out during triage.

### 7. Contributing Factors
Secondary conditions that exacerbated the incident or slowed resolution:
- Missing socket reuse flags (`SO_REUSEADDR`).
- Excessively long scrape or debounce intervals (`for: 5m`).
- Transient process delays or cgroup lockups.

### 8. Recovery Actions
The precise step-by-step remediation executed to resolve the fault:
- Commands executed.
- Subprocesses stopped or restarted.
- Files or volumes cleaned.

### 9. Post-Remediation Verification
Empirical evidence proving the service has returned to full operational health:
- HTTP 200 OK responses with response latency.
- PromQL queries returning normal baseline values.
- `systemctl is-active` returning `active`.

### 10. Preventive & Corrective Actions
Concrete action items categorized as:
- **Prevent**: Architectural hardening to prevent recurrence.
- **Mitigate**: Faster detection, shorter alerts, or automated remediation.
- **Process**: Documentation, runbook updates, or dashboard additions.

## 3. Reference RCA Example: Incident SRE-007 (Monitoring Agent Failure)

```markdown
# Incident Report: SRE-007 — Custom Monitoring Agent Failure

**Date:** 2026-10-28 15:18:00 IST  
**Incident Lead:** Agent 10 (SRE Failure Simulation Engineer)  
**Status:** Resolved (Empirically Verified)  
**Severity:** SEV-2 (Observability Blindspot)  

### 1. Incident Summary
On 2026-10-28 at 09:48:00 UTC, the Custom Python Monitoring Agent running on port 9101 was terminated via SIGTERM to simulate unexpected daemon failure. Prometheus scrape attempts failed with connection refused, creating an observability blindspot for custom host metrics. The automated remediation controller detected the outage, executed an idempotent service restart via the project virtual environment, and restored telemetry in 3.902 seconds.

### 2. Impact
- **Service Affected**: Custom Python Monitoring Agent (`http://127.0.0.1:9101/metrics`).
- **SLI Impact**: Agent Availability SLI dropped to 0% for 9.889 seconds.
- **Error Budget Consumed**: 0.00038% of monthly 99.9% error budget.
- **Total Duration**: 9.889 seconds.

### 3. Timeline
- `09:48:00.321 UTC`: SIGTERM dispatched to agent PID 1619270.
- `09:48:05.926 UTC`: Detection health probe confirms port 9101 connection refused (MTTD: 5.926s).
- `09:48:06.010 UTC`: Automated triage confirms agent down; remediation handler invoked.
- `09:48:06.120 UTC`: Remediation controller verifies preconditions and checks circuit breaker.
- `09:48:07.100 UTC`: Controller cleans lingering PID and launches agent via `.venv/bin/python3 -m agent.main`.
- `09:48:10.022 UTC`: Agent initializes HTTP server and binds socket on 127.0.0.1:9101.
- `09:48:10.210 UTC`: Verification probe receives HTTP 200 OK from `/healthz` (MTTR: 3.902s).

### 4. Detection Method
- High-frequency health assertion: `curl -s -f -m 1 http://127.0.0.1:9101/healthz`.
- Prometheus Rule: `TargetDown{job="python-agent"}` (`up == 0`).

### 5. Symptoms
- Prometheus TSDB: `up{job="python-agent"} = 0`.
- Scrape error: `dial tcp 127.0.0.1:9101: connect: connection refused`.
- Agent log: `Received signal SIGTERM. Stopping agent...`.

### 6. Root Cause
- **Confirmed**: Graceful termination via SIGTERM unmapped the agent process and closed port 9101.
- **Hypothesis Disproven**: Memory leak / OOM kill — ruled out; system memory remained >7GB available.

### 7. Contributing Factors
- Sockets in `TIME_WAIT` initially delayed daemon restart; mitigated by setting `allow_reuse_address = True` in `agent/server.py`.

### 8. Recovery Actions
- Executed `scripts/reliability/remediation/remediate_agent.sh`.
- Reclaimed port 9101, purged stale PID file, and spawned new daemon inside `.venv`.

### 9. Verification
- `/healthz` returns `{"status":"ok"}` with HTTP 200.
- Prometheus scrape target transitions to `health: "up"` on subsequent 15s evaluation.

### 10. Preventive Actions
1. **[DONE]** Configured `ThreadingHTTPServer.allow_reuse_address = True` to prevent socket bind failures during rapid restarts.
2. **[PLANNED]** Package Python agent as a managed systemd unit (`linux-monitoring-agent.service`) with `Restart=always` and `RestartSec=2s`.
```
